Motivation and Key Figures

Why was this package created, what's the main purpose, key-figures like number of users etc.

  • Bad quality of Purchase master data
  • High percentage of wrong prices
  • function for mass maintenance on business object level not available (only on field level)
  • function for mass maintenance of scales not available
  • increase data quality with business object focus
  • Excel down and upload functionality
  • connection of other interfaces possible (e.g. Portal)
  • One entry point to a cockpit for mass maintenance (reduction of ERP Codes)

Solution overview – Info record Cockpit

Abstract

Cockpit for mass maintenance of purchasing info records

Explicit functions

  • Info-record change
  • Create/update price condition periods
  • Add info-memo
  • Add attachment to the info-record
  • Create/Enhance info-record (to create new EINE view records for existing info-record)
  • Copy info-record (to copy info-records from one vendor to another one)
  • Maintain info-record PO text

Benefits & Usage – Info Record Cockpit

  • APIs can be connected to different UIs or other source systems
  • Mass change, creation and enhancement of info records
  • Mass maintenance of price condition periods for info records inclusive all valid condition types as well as scales.
  • EXCEL interface for provide the data to be maintained via EXCEL upload

Adding texts to info memo text field via mass change

Add a attachment to info records via mass change

Replacement of purchase order text in info records via mass change

13.6.1.1.  Function module /RB4R/MM_PUR_INFOREC_COND

The Function module /RB4R/MM_PUR_INFOREC_CONDITN responsible for selection and display of condition data in the module pool screen 300.

It performs below steps,

13.6.1.1.1. Instantiate change data reference handles for ALV source , excel source and download excel based on the Info-record maintenance class /RB4R/MM_CL_INFORECORD class reference.
13.6.1.1.2. Instantiate original data reference handles for ALV source , excel source based on the Info-record maintenance class /RB4R/MM_CL_INFORECORD class reference.
13.6.1.1.3. Data selection of data from EINA , EINE , KONH , KONP and scales details using the Method GET_CONDITION_DATA of the class /RB4R/MM_CL_INFORECORD. Only Quantity scales are considered.
13.6.1.1.4. Creation of Field-catalog based on public attribute MT_FIELDLIST from Info-record maintenance class /RB4R/MM_CL_INFORECORD class reference.
13.6.1.1.5. Creation of custom tool bar with icons and ALV layout settings is performed to display the data using custom container reference CALL METHOD go_grid_300→set_table_for_first_display.
13.6.1.1.6. ALV Report gets displayed based on the display attributes from template table /RB9S/PROC_INFOD settings.

13.6.5.3. Function module /RB4R/MM_API_INFO_SAVE

This function module API will be used to save inforecord data EINA/EINE/KONH/KONP/KONM details for Inforecord maintenance.

  1. Assign the current SAP system id value to the return parameter of the EV_SYSTEM_ID.
  2. Assign the incoming external id value to the return parameter of the EV_EXTERNAL_ID.
  3. Perform customer  adjustment in DATAX structure and convert the incoming inputs into SAP format for validation.

  1. The enhancement section  /RB4R/MM_API_INBOUNDX  is provided for developing the customer specific logic for the custom fields in each target system.
  2. Based on the below utility class , the mapping of inbound data takes place.
    1. CALL METHOD  /rb4r/mm_cl_api_info_utility=>map_inbound_data
  3. During Mapping of inbound data, the database values are fetched for EINE/EINA/KONP and compared with the inbound data. Then the resulted records are determined using merge of both entities and as per its corresponding X- Structures.
  4. The enhancement section /RB4R/MM_API_INBOUND  is provided for developing the customer specific logic for the custom fields in each target system
  5. Incase of any error during inbound mapping, then SAVE operation terminates and error messages returned to ET_RETURN.
  6. Incase of no errors, then following operations are performed.
    1. Validation of data
    2. Save
  7. Perform validation on all inputs data by using the utility class
    1. CALL METHOD /RB4R/MM_CL_API_INFO_UTILITY=>validate_data
  8. The result of the validations are returned to ET_RETURN.
  9. Depends upon the type of mode, the save operation takes place.
  10. When the background mode is initial (IV_BACKGROUND_MODE = ' '), then Synchronous processing takes place by using utility class CALL METHOD /RB4R/MM_CL_API_INFO_UTILITY=>save_data
  11. When the background mode is 'X' (IV_BACKGROUND_MODE = 'X' ), then ASynchronous processing takes place by using background job via submit program /RB4R/MM_PUR_INFOREC_API_JOB and spool number is returned in EV_JOB_NAME and  EV_JOB_ID.

13.12.  Phase out Concept

Phasing out this product is pretty straightforward, as it works completely on its own namespace, having all associated objects in a single package. In order to decommission this product, phase-out (technically deletion) transports prepared in CD system have to be imported to the target system.  To completely delete the product from the system, it would require a deletion transport from DC7 system. This deletion transport must include all the objects of the objects for the respective version of the tool.

Please note that if any development or enhancement implemented locally in target system on top of this CD product, all of them have to be removed from the target system before importing the phase-out transports.
