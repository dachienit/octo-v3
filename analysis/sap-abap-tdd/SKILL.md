# sap-abap-tdd

Everything this analysis needs is decided by one driver script. You do not plan the
steps, you do not choose commands, and you do not write the document. You run the
driver and do what it says.

## The loop

1. Work out two values:
   - `<SAP_SYSTEM>` — the system the user named (for example `D8R`). If the user did not
     name one, call the `adt` tool with `{"argv": ["-q", "auth", "profile", "list"], "label": "Which SAP system"}`
     and use `defaultProfile`. If that is empty, STOP and ask the user which system.
   - `<PACKAGE>` — the package the user named, exactly as given (for example `/RB4R/MM_PUR_DAT_COCKPIT`).
2. Run the driver `scripts/next.py` of this skill with bash. Its absolute path is the path
   you just used to read this SKILL.md, with the last part `SKILL.md` replaced by
   `scripts/next.py` — change nothing else in it (bash does not start in the skill folder,
   so a relative path does not work):

   | You read                            | You run                                    |
   |-------------------------------------|--------------------------------------------|
   | `<...>/skills/sap-abap-tdd/SKILL.md` | `<...>/skills/sap-abap-tdd/scripts/next.py` |

   ```bash
   python "<...>/skills/sap-abap-tdd/scripts/next.py" --system <SAP_SYSTEM> --package "<PACKAGE>"
   ```

   Copy the package name character by character from the user's message. If `python` is
   not found, use `python3`. From the second round on, run exactly the command the driver
   prints after `THEN:`.

   Add `--new` only if the user asks to analyse again from scratch a package that was
   analysed before. Add `--with-prose` only if the user explicitly asks for a written
   introduction. Never add either on your own.
3. The driver prints one `STEP` with one `ACTION`. Do exactly that:
   - **`adt` tool call** — copy the JSON it prints verbatim into the `adt` tool. Change nothing.
   - **`sapgit` tool call** — copy the JSON verbatim into the `sapgit` tool.
   - **writing task** (only with `--with-prose`) — read the one packet file it names, then
     write exactly the files the driver names.
4. Run the driver again — the exact command is printed after `THEN:`.
5. Repeat until the driver prints `DONE` or `STOP`.
   - `DONE` → tell the user where the document is and list the limitations it printed.
   - `STOP` → report its message verbatim and ask the user how to proceed.

A run takes a handful of rounds (one per package snapshot, plus a few lookups). Keep
going without asking the user between rounds. Do not reply to the user, summarise or
attach anything until the driver prints `DONE` or `STOP` — an `adt` call is never the
end; the next step is always to run the driver again. Only the driver can print `DONE`.

## Rules

1. **Only the driver decides.** Never run an `adt` or `sapgit` command the driver did not
   print, never change its arguments, never skip a round. If a tool call fails or returns
   nothing, do not retry or work around it — just run the driver again; it checks the
   result on disk and decides.
2. **bash is only for running the driver.** Not for `ls`, `mkdir`, `cat`, `echo`, `printf`,
   `bash -lc` or anything else.
3. **SAP is the source of truth.** Do not read or edit the package folder under
   `artifacts/<SAP_SYSTEM>/` — the user may be editing those objects live. The driver
   takes its own snapshot into `artifacts/<SAP_SYSTEM>/.scratchpad/`.
4. **Do not write the technical document yourself.** The driver generates every chapter
   from the snapshot and validates the result. The Functional Description stays as the
   template has it, for the functional team — do not fill it in.
5. **In a writing task:** use only facts from the packet; name objects exactly as they
   appear there; write English HTML fragments with `<h3>`/`<h4>` at most — never
   `<h1>`/`<h2>`, `<script>` or `<style>`. The driver rejects fragments that name objects
   which do not exist in the snapshot, and hands the task out again.
